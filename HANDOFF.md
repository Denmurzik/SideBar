## Итог: как интегрировать Quick Share — рекомендованный (финальный) вариант

**Вариант A — делегировать отправку официальному приложению.** Свой OAuth-клиент, сертификаты
и переопределение протокола не нужны.

```
CreateProcess("C:\Program Files\Google\NearbyShare\nearby_share.exe", "\"путь\\к\\файлу1\" \"путь\\к\\файлу2\" ...")
```

Проверено экспериментально (2026-10-19, эта машина):
- Если `nearby_share.exe` ещё не запущен — стартует сам и открывает файл в режиме отправки.
- Если уже запущен — второй вызов пишет в лог `Another instance is already running, command line: <файл>`,
  передаёт команду работающему экземпляру через `WM_COPYDATA`, файл добавляется в очередь отправки
  (строки в бинарнике: `We are the only instance, command line:`, `Opening file from command line.`,
  `Received WM_COPYDATA`).
- Подтверждено скриншотом окна «Быстрая отправка» (class `Google.Windows.NearbyShare`) после двух
  запусков: оба файла в очереди, в «Устройства поблизости» виден реальный `Pixel 9` — режим
  «Свои устройства» (self-share) работает сам, потому что официальное приложение уже вошло в
  аккаунт пользователя и само управляет своими сертификатами/токенами.

Почему именно так: официальный MSIX регистрирует Quick Share как `windows.shareTarget`
(приёмник системной панели «Поделиться») и как `windows.fileExplorerContextMenus`
(COM-сервер `nearby_share_context_menu.dll`, CLSID `AD54D7CA-052D-4730-B0F2-2BA34D3438DC`) —
пункт «Отправить через Quick Share» в проводнике использует тот же механизм запуска с файлом.
Отдельного публичного CLI-контракта Google не документирует, но поведение воспроизводимо и
устойчиво на уровне именно этого механизма (WM_COPYDATA между экземплярами — штатный Windows-паттерн
single-instance приложений, не хрупкий хак).

Альтернатива без вызова exe напрямую — системная панель «Поделиться» Windows
(`IDataTransferManagerInterop`/`DataTransferManager`), пользователь сам выбирает Quick Share
из списка. Официально, но лишний клик пользователя.

## Продвинутый/запасной вариант — свой протокол + самостоятельное обновление сертификатов

Нужен **только** если требуется приём файлов, статусы внутри своего UI, или работа без
установленного официального приложения (своя реализация протокола Nearby, как у NearDrop/
NearShare, в открытом режиме `EVERYONE`). Последнее, что было проработано по этому пути —
механизм обновления сертификатов для режима «Свои устройства» без постоянно открытого
официального приложения:

**Наблюдение из логов `nearby_share.log`:** при каждом запуске `nearby_share.exe`,
без клика пользователя, автоматически — за ~1–2 секунды:
1. `nearby_share_certificate_manager_impl.cc` проверяет валидность сертификатов.
2. Планировщик `upload_local_device_certificates` запускается немедленно.
3. `authentication_manager_impl.cc` обновляет access-токен через `oauth2.googleapis.com/token`.
4. gRPC-вызов `NearbyService.PublishDevice` — загружает self-share/contact сертификаты.
5. Лог `PublishDevice succeeded`.

Планировщик сам показывает нужную частоту: `upload_local_device_certificates` — раз в ~24 часа,
`private_certificate_expiration` — проверка раз в ~50 часов. Значит, держать официальное
приложение открытым постоянно не нужно — достаточно **фонового периодического запуска**:

1. Запустить `nearby_share.exe` программно.
2. Подождать до появления `PublishDevice succeeded` в логе (или фиксированную паузу ~10–15 с).
3. Закрыть процесс аккуратно (не `taskkill /F` сразу — дать секунду на запись в leveldb
   `NearbySharePublicCertificateDatabase`).
4. Свой клиент в остальное время читает уже обновлённые `preferences.json` (свои приватные
   сертификаты: `key_pair`, `secret_key`, `metadata_encryption_key`, `consumed_salts`) и
   `NearbySharePublicCertificateDatabase` (leveldb, публичные сертификаты контактов/устройств
   аккаунта) и сам реализует воздушный протокол (BLE-реклама + UKEY2 + шифрование метаданных).

Это не подмена OAuth-клиента Google (в отличие от варианта «вытащить refresh-токен и дёргать
`nearbysharing-pa.googleapis.com` от своего имени» — тот путь завязан на зашитые в официальном
приложении `client_id`/`client_secret` первопартийного клиента и признан нарушением ToS, не
рекомендован). Здесь просто автоматизируется запуск легитимного установленного приложения.

Риски, которые не сняты:
- Нет headless/CLI-флага для скрытого запуска — вероятно короткое мигание окна/иконки в трее.
- Устойчивость к принудительному завершению процесса не проверялась (leveldb обычно переживает
  аварийное завершение, но не проверено на этом механизме конкретно).
- В бинарнике есть серверный endpoint `/v1/abuse` — у Google точно есть антиабуз-логика на
  identity/nearby RPC; раз в сутки запуск-обновление-закрытие — низкочастотный паттерн, но
  гарантии, что он не попадёт под какие-то эвристики, нет — не проверялось эмпирически.

## Технические факты о протоколе (для справки, если понадобится свой клиент)

- Архитектура установленного Quick Share: `nearby_share.exe` — Flutter + статически слинкованный
  нативный C++-стек; `data/libnearby_share.so` — Dart AOT-снэпшот (UI/логика на Dart,
  `package:location.nearby.apps.better_together` — внутреннее кодовое имя).
- Код совпадает с открытым `github.com/google/nearby` (Apache 2.0) — имена классов и protobuf
  совпадают один в один.
- Протокол: 3 слоя кадров — медиумы (`location.nearby.mediums.*`) → транспорт Nearby Connections
  (`location.nearby.connections.OfflineFrame`/`V1Frame`) → прикладной Quick Share
  (`nearby.sharing.service.proto.*`).
- Безопасность: UKEY2 handshake → SecureGcm/SecureMessage/D2D (AES + HMAC).
- Обнаружение: BLE service UUID `0xFEF3` (Fast Initiation), затем апгрейд полосы на
  Wi-Fi Direct/LAN для самой передачи файлов.
- Google-аккаунт/self-share: скоуп `https://www.googleapis.com/auth/nearbysharing-pa` —
  приватный, только для первопартийных клиентов Google (подтверждено по GAIA-константам
  Chromium); свой OAuth-клиент его не получит.

## Окружение

- Windows 11, bash (git bash) как шелл; `wmic` в этом bash недоступен — для чтения RAM и т.п.
  использовать PowerShell через `Get-CimInstance`, записывая скрипт во временный `.ps1`-файл
  и запуская `powershell -NoProfile -ExecutionPolicy Bypass -File <script>.ps1` (инлайновый
  `-Command` с `$переменными` съедается самим bash).
- REA установлен (`npm install --global rea-agents`), команда `rea`. Нативная декомпиляция
  (Ghidra/IDA/Hopper) **не настроена**: Hopper не поддерживает win32, Ghidra требует
  `GHIDRA_INSTALL_DIR` (12.1.x), IDA требует `REA_IDA_MCP_CONFIG`. Kuna в принципе не умеет
  формат PE (только ELF/thin Mach-O).
- Декомпиляция `nearby_share.exe` (47 МБ) Ghidra не запускалась: на машине в моменты сессии
  было ~2.9–5 ГБ свободной RAM, а для Ghidra на бинарнике такого размера нужно ~8–10 ГБ —
  запускать только после высвобождения памяти.
- Путь установки Quick Share: `C:\Program Files\Google\NearbyShare` (сборка от 2026-01-13).
- Данные пользователя: `C:\Users\<user>\AppData\Local\Google\Nearby\Sharing\` —
  `preferences.json` (приватные сертификаты, открытый JSON), `NearbySharePublicCertificateDatabase\`
  (leveldb), `Logs\nearby_share.log`, `nearby_cookies.json`.

## Грабли

- `rea analyze <папка>` ошибочно распознаёт директорию приложения как JavaScript/Electron-проект,
  если внутри есть что-то похожее на `FontManifest.json` — указывать конкретный бинарник, а не
  папку целиком.
- `rea inspect-dart-aot` ожидает путь к **APK** с Flutter-пейлоадом внутри, а не отдельный
  Dart AOT `.so`-файл — для автономной Windows-установки не подошёл, пришлось вытаскивать строки
  обычным `strings -n 6 <file>`.
- Символы в `nearby_share.exe` **не вырезаны** (MSVC mangled names) — полные имена классов/методов
  C++ (`NearbySharingServiceImpl::OnIncomingAdvertisementDecoded` и т.п.) восстанавливаются прямо
  из `strings`, без декомпилятора — для первого прохода реверс-инжиниринга декомпилятор не
  обязателен.
