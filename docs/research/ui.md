# UI-спайки (S7, S10, S8)

Код: `spikes/ui/`. Окружение: Windows 11 (10.0.26300), .NET SDK 10.0.402, VS Build Tools 2026, 15.5 ГБ RAM.

## S7 — WinUI 3 + NativeAOT, фоновая память

Проект `spikes/ui/S7Panel` (unpackaged, `WindowsAppSDKSelfContained`, `PublishAot`), окно без рамки, always-on-top,
`IsShownInSwitchers=false`, у правого края `DisplayArea.Primary.WorkArea`; режимы show/hide (`AppWindow.Hide()` +
`EmptyWorkingSet` + `SetProcessWorkingSetSize(-1,-1)`). Google.Protobuf 3.36.2 + сгенерированный `Ping`
(string/int32/repeated bytes/map), на старте сериализация и разбор туда-обратно.
Замер: `spikes/ui/measure.ps1 -Dir <папка публикации> -Label <имя>` (приложение управляется именованными событиями
`S7Panel_show|hide|exit`, время первого кадра пишет в `s7.log`).

**Проверено (результат запуска):**

| Метрика | NativeAOT | JIT (self-contained, без trim) |
|---|---|---|
| Размер публикации | **85.6 МБ** (150 файлов; S7Panel.exe 5.7 МБ) | 170.4 МБ |
| Protobuf: round-trip | ok, 22 байта, без IL-предупреждений при публикации | ok |
| После старта (6 с): private bytes / WS / private WS | 84.0 / 139.0 / 64.1 МБ | 85.6 / 154.2 / 65.1 МБ |
| Скрыто +2 с после обрезки: WS / private WS | 8.0 / **3.0 МБ** | 10.9 / 3.3 МБ |
| Скрыто +10 с: WS / private WS | 8.6 / 3.5 МБ | 14.5 / 4.8 МБ |
| Скрыто +60 с: WS / private WS | 14.4 / 7.6 МБ | 23.6 / 8.9 МБ |
| После показа (+3 с): WS / private WS | 31.3 / 12.4 МБ (2-й, 3-й цикл: ~21 / 8–9 МБ) | 44.0 / 15.1 МБ (далее ~28 / 9 МБ) |
| Показ после обрезки → первый `CompositionTarget.Rendering` (3 цикла) | 12.9 / 4.3 / 15.7 мс | 11.1 / 16.5 / 10.4 мс |

Выводы:
- NativeAOT работает с WinUI 3 (WinAppSDK 2.x, split-пакеты) и Google.Protobuf без предупреждений и падений. Критерий S7 (<100 мс на показ) выполнен с большим запасом; цель «единицы МБ private WS в простое» — выполнена: **~3 МБ сразу после обрезки, ~4–8 МБ через 10–60 с**.
- Private bytes (commit) обрезкой не уменьшаются (~84–89 МБ у обоих) — это зарезервированные/закоммиченные страницы, не ОЗУ. В диспетчере задач важен WS/private WS.
- В скрытом состоянии WS медленно растёт (3 → 7.6 МБ за минуту у AOT): что-то в процессе периодически трогает страницы (таймеры XAML/Composition, WinRT-потоки). В продакшене — повторять обрезку по таймеру (например раз в 30–60 с, пока панель скрыта).
- AOT выигрывает у JIT: ×2 по размеру, ~20–35 % по WS после показа. Старт-WS (~140 МБ) одинаков — это нативный стек WinUI.
- Оговорка по «первому кадру»: `Rendering` срабатывает в начале кадра, реальный present может быть чуть позже (+1 кадр). Порядок величины верен.
- Не проверено: холодный старт процесса до первого кадра, поведение при нескольких мониторах/DPI.

Подводные камни сборки (зафиксировать в CI):
1. NativeAOT-линковка из git-bash: `vswhere.exe` не в PATH → `export PATH="/c/Program Files (x86)/Microsoft Visual Studio/Installer:$PATH"`. MSVC-линкер ILCompiler находит сам.
2. Grpc.Tools в этом проекте не запускал `Protobuf_Compile` перед компиляцией (WinUI-цели) — добавлен явный `<Target Name="GenProto" BeforeTargets="CoreCompile;MarkupCompilePass1" DependsOnTargets="Protobuf_Compile" />`.
3. Мета-пакет `Microsoft.WindowsAppSDK` тянет AI/ML-зависимости; используем split-пакеты Base/Foundation/WinUI/InteractiveExperiences.
4. Команды: `dotnet publish -c Release -p:Platform=x64 -o out-aot -m:1` (AOT) и с `-p:Aot=false -o out-jit` (JIT).

## S10 — пружинный выезд панели

Проект `spikes/ui/S10Spring` (JIT: `out-jit/`, NativeAOT: `out-aot/` — обе собираются и запускаются). Один exe, режимы:
`--mode A|B`, `--backdrop none|transparent|element|win-acrylic|win-mica`, `--ct ex|rgn|key|tr|none` (click-through), `--fill dark|none`,
`--solid` (пурпурная заливка для автотестов), `--cursor` (сам реагирует на курсор: край → open, ≤1 см → peek, уход + 300 мс → скрыть),
`--spring <ζ>,<Period мс>` (A), `--bresp <сек>` (B). Команды для автотестов — именованные события `S10_open|peek|close|exit`.
Инструменты: `trace.ps1` (снимает по экрану положение края панели ~60 раз/с во время сценария), `hit.ps1` (кто владеет окном под точкой — проверка click-through), `shot.ps1` (скриншот), `an.py` (разбор трассы).

Монитор на этой машине один: 1920×1080 @ **60 Гц** (Intel Arc, предельно 60). 120/144 Гц проверить нельзя — только рассуждение и проверка пользователем.

### Проверено (измерения)
- **Пружина Composition (A):** `SpringVector3NaturalMotionAnimation` (ζ=0.8, Period=60 мс) на `Translation` панели. Кадры UI-потока за выезд: mean 16.6 мс, p99 17.5, late=0. Положение по скриншотам плавное, без скачков.
- **Прерывание (A):** команда `close` через 200 мс после `open` — видимая ширина продолжает расти ещё ~50 мс (280→309 px) и затем разворачивается: скорость подхватывается без рывка. То же для `open` во время закрытия, `peek`→`open`→`close` подряд. Явно InitialVelocity задавать не пришлось (повторный `StartAnimation` на то же свойство сохраняет скорость).
- **Пружина `SetWindowPos` (B):** аналитическая затухающая пружина (ζ=0.8, response 0.35 с), позиция считается по QPC в `CompositionTarget.Rendering`. Кадры: mean 16.66 мс, p99 17.6, late=0 (без нагрузки). Прерывание с сохранением скорости — аналитически (новое состояние = текущие x, v). Кривая почти идентична A; B даёт реальный перелёт за целевое положение.
- Реакция на команду (команда → первые пиксели): A ~60–80 мс (включая `Show` окна), B ~50 мс.
- **Click-through (A, окно 340 epx на правом краю), `hit.ps1`:**
  | способ | peek (окно показано, видна полоска 12 px) | open |
  |---|---|---|
  | `WS_EX_LAYERED\|WS_EX_TRANSPARENT` (`ex`) | вся область сквозная — клики проходят | панель ловит клики |
  | `SetWindowRgn` на полоску 12 px (`rgn`) | сквозная, кроме самой полоски 12 px | панель ловит клики |
  | `WS_EX_TRANSPARENT` без LAYERED (`tr`) | **не** сквозная (работает только внутри потока) | — |
  | ничего | окно целиком блокирует клики | — |
  В B (окно сдвинуто, на экране только 12 px) сквозность в peek работает тем же `ex`.
- **Прозрачность окна WinUI 3 (A):** окно без Backdrop рисуется **чёрным**, не прозрачным; `DwmEnableBlurBehindWindow`, `WS_EX_LAYERED`+color key — не помогают (на скриншотах чёрный остаётся). Работает **собственный `SystemBackdrop` с полностью прозрачной кистью** (`TransparentBackdrop.cs`): пиксели под панелью совпадают с экраном без панели (0/315 отличий). Нюансы: (1) кисть должна быть `Windows.UI.Composition.CompositionBrush` (в WinAppSDK 2.x), а `new Compositor()` на UI-потоке падает (`DispatcherQueue`) — компоситор создаётся на вспомогательном потоке с `CreateDispatcherQueueController` (CoreMessaging.dll); (2) **`WS_EX_LAYERED` ломает прозрачность** (снова чёрный) — click-through только через `SetWindowRgn`; (3) работает и под NativeAOT (проверено запуском `out-aot`).
- **Mica/Acrylic в A:** оконный `DesktopAcrylicBackdrop`/`MicaBackdrop` занимает всё окно и не двигается вместе с контентом, поэтому для A используется `SystemBackdropElement` с `DesktopAcrylicBackdrop` внутри панели поверх прозрачного окна — рендерится без ошибок (в т.ч. AOT), панель серая «акриловая». Правильность размытия именно фона рабочего стола по скриншоту не подтверждена — посмотреть глазами.
- Окно A обрезает перелёт: контент не выходит за границы окна (пик виден как 337 px = ширина окна). Для пружины с перелётом у открытой позиции нужен запас ширины окна (+~40 epx прозрачного поля) либо ζ≥1 на открытии.

### Не проверено / нужна проверка глазами
- Плавность на 120/144 Гц (нет такого монитора), под нагрузкой на UI-поток.
- Реальный вид Acrylic в `SystemBackdropElement` и в B (`--backdrop win-acrylic`), тени/углы.
- Тонкая белая линия 2 px у левого края окна на всех скриншотах (DWM-рамка/`WS_THICKFRAME`; `DWMWA_BORDER_COLOR`, `WS_POPUP` не убрали) — нужно устранить в M1.

### Рекомендация: вариант A (неподвижное прозрачное окно + пружина Composition)
Обоснование: анимация идёт в потоке композитора — на 120/144 Гц она не зависит от загрузки UI-потока (внутри панели будут ещё анимации стопки/списка устройств), прерывание штатно сохраняет скорость, Acrylic двигается вместе с контентом (`SystemBackdropElement`), окно в скрытом состоянии просто `Hide()`. Цена: свой `TransparentBackdrop` (хак с отдельным потоком), запрет `WS_EX_LAYERED`, click-through через `SetWindowRgn` (в peek кликабельна полоска 12 px — это и так зона «касания края»), запас ширины под перелёт.
Запасной вариант: B уже работает в том же exe (`--mode B`), даёт то же на 60 Гц без хаков и с оконным Mica/Acrylic; переходить на него, если на 120/144 Гц A окажется хуже или откажет прозрачность на других конфигурациях GPU.

### S10-addendum: ОЗУ с Acrylic (NativeAOT, `measure10.ps1`, скрытие = `Hide()` + `EmptyWorkingSet`)

|---|---|---|
| Запуск, +6 с (обрезки ещё не было), WS / private WS | 70.6 / 38.3 МБ | 68.6 / 37.7 МБ |
| Показано +2 с | 80.5 / 46.4 | 77.2 / 44.7 |
| Скрыто +2 с | 11.7 / **3.5** | 7.1 / **2.3** |
| Скрыто +10 с | 11.9 / 3.6 | 7.1 / 2.3 |

Выводы: acrylic почти не добавляет к фону (private WS в скрытом виде 2–4 МБ, как без него); в A на ~1 МБ больше (доп. поток компоситора + element). После `Hide()`+`EmptyWorkingSet` и повторного показа acrylic восстанавливается: пиксели панели на скриншотах до и после идентичны (A 44,44,44; B 42,42,42), не чёрные и не пустые (проверено `shot`-ами, `open1/open2-*.png`).

Не проверено: оконный акрил + `SetWindowRgn` по кадрам (не нужен для A), скруглённые углы Win11 на акриле (у элемента скругление задаётся `CornerRadius` самого элемента; у B — DWM-углы окна, в тестах отключены `DWMWA_WINDOW_CORNER_PREFERENCE=DONOTROUND`), реальный вид размытия — глазами.

## Перенастройка под макет «карточка» (2026-10-22)

Геометрия: карточка 144×276 epx (плитки 120 + отступы 12), скругление 16, отступ 8 epx от края, по центру правого края основного монитора; peek — видно 10 epx; зона срабатывания по Y — карточка ± 1 см; свой бордер 1 физ. пиксель (`BorderThickness = 1/RasterizationScale`, цвет по теме), DWM-рамка выключена (`DWMWA_BORDER_COLOR = NONE`, углы окна DONOTROUND).

**S10Spring (проверено, 100 % DPI):**
- Вариант A: окно = карточка + 200 epx прозрачного запаса слева (веер/перелёт пружины) + по 40 epx сверху/снизу; контент едет `Translation` (open 0, peek 142, hidden 152 epx). Click-through регионом: пока идёт пружина — весь прямоугольник окна (иначе обрежется контент), после settle — скруглённый регион карточки (open) / полоска 10 epx (peek); hidden — `Hide()`. `hit.ps1`: peek — кликабельна только полоска (`right-4` PANEL, `right-100` other); open — карточка PANEL, зазор у края и запас слева (веер) — other.
- Вариант B: окно = ровно карточка, `SetWindowRgn` со скруглением один раз, оконный `DesktopAcrylicBackdrop`, двигается по пружине; peek/hidden — click-through через `WS_EX_LAYERED|TRANSPARENT`.
- Скриншоты `cA/cB-crop.png`: карточки скруглены, 1-px серая обводка видна, **белой 2-px линии больше нет** (её давала рамка DWM). Для 125/150 % — рассуждение: толщина в epx = 1/scale даёт ровно 1 физ. пиксель, но на дробном масштабе XAML может сглаживать линию; проверить на реальном 125/150 % (не проверено).
- Плавность на 60 Гц одинакова (A: кадры mean 16.67/p99 17.7, late 0; B: 16.5–16.7/17.2, late 0), прерывание сохраняет скорость в обоих (трассы `trA/trB.csv`).
- ОЗУ с Acrylic на этой геометрии (NativeAOT, скрыто = `Hide()`+`EmptyWorkingSet`, private WS): A: скрыто +2 с 3.6, +10 с 3.6, +60 с 4.5, показано 8.2 МБ; B: 2.4 / 2.4 / 3.3 / 7.4 МБ.
- **Рекомендация: A остаётся.** Для маленькой карточки B проще и дешевле (нет прозрачного хака, оконный акрил и скругление регионом), и если бы веера не было — выбрал бы B. Но веер уходит влево за карточку: в B нужно либо второе окно под веер, либо менять размер окна на лету; в A запас уже есть, пружина идёт в потоке композитора (важно на 120/144 Гц и когда UI занят анимациями внутри). Решение сменить на B оправдано, только если пользователь увидит на 120/144 Гц, что A хуже.

**S8Edge/S8Drive (под карточку):** окно = карточка, зона по Y карточка ± 1 см (PeekPx), overPanel — только по высоте карточки. `S8Edge` собирается JIT/AOT без предупреждений; хук ставится (`hook installed=True`), все окна WinUI перечисляются.
- Находка: у окон WinUI 3 нет свойства `OleDropTargetInterface` (ни у top-level, ни у `DesktopChildSiteBridge`/`InputSiteWindowClass`; `RevokeDragDrop` даёт «не зарегистрировано») — перехват через прокси над таргетом WinUI не получится. Вместо этого S8Edge сам регистрирует `IDropTarget` (`RegisterDragDrop`, hr=0, после `OleInitialize`) на дочерних окнах и читает нативный `IDataObject`: `CF_HDROP`, `FileGroupDescriptorW`+`FileContents` (HGLOBAL/IStream). COM-интерфейс — `[GeneratedComInterface]`, работает под NativeAOT.
- **Не проверено (ждёт запуска пользователем):** весь OLE-сценарий — хук получает движения во время drag из OLE (`lbutton=True`), панель открывается при drag, drop обычных и виртуальных файлов, drag-out нескольких и `DropResult` (Copy/None). Автотест `S8Drive` это проверяет и печатает PASS/FAIL; без него это гипотезы. Известное ограничение: нативный `IDataObject` читается синхронно внутри `Drop` (для больших виртуальных файлов нужен фоновый поток с маршалингом интерфейса).
- Детект «активного drag» в fullscreen: надёжного признака чужого OLE-drag нет; в коде используется «ЛКМ зажата при входе в зону» (`GetAsyncKeyState`) — эвристика (ложные срабатывания при зажатой ЛКМ в игре у края).

### Карточка 144×468 epx и светлая рамка (2026-10-22)
- Размеры: карточка 144×468 epx, плитки 120×216 (в демо плитки 216 высотой по ряду), зона по Y в S8Edge/S8Drive — от новой высоты.
- **Причина светлой линии по контуру** (скриншот пользователя, режим B): окно `OverlappedPresenter` без рамки всё равно имеет 3 px non-client рамку (`WS_DLGFRAME`, стиль возвращается WinUI после снятия) — она сдвигала XAML-контент на 3 px (client 138×462 в окне 144×468) и просвечивала светлым акрилом. Исправление: сабкласс окна, `WM_NCCALCSIZE` (wParam≠0) → 0 (+`SWP_FRAMECHANGED`) — client = окно целиком (проверено логом: `client@(1920,306) size 144x468`). На скриншоте B после правки светлой линии нет, остаётся только своя серая 1-px обводка. Тот же приём применён в S8Edge.

### Исправление выводов S10: прозрачность варианта A НЕ подтверждена; рекомендация меняется на B (2026-10-22)
Проверка углов (зум ×8 + попиксельно) выявила, что ранее принятый вывод о прозрачном окне в A был ошибочным:
- Окно A с `TransparentBackdrop` (прозрачная кисть) **рисуется чёрным** там, где XAML ничего не нарисовал (в запасе слева и в углах): пиксели (0,0,0) против обоев 30–44 при скрытой панели (`--ct none --fill none`; то же с `--keepframe`). Мой прежний тест «0/315 отличий» был некорректен — в той конфигурации окно просто не было видно. Предыдущие «красивые» скриншоты A получались только потому, что `SetWindowRgn` вырезал чёрное; скруглённый регион даёт ступенчатые края и срез АА обводки, прямоугольный регион оставляет чёрные уголки вне дуги (за контуром радиуса 8).
- Следовательно, для A нужна настоящая прозрачность окна (не найдена в этой версии WinAppSDK: нет `TransparentTintBackdrop`, прозрачная кисть не помогла), иначе углы и запас под веер невозможны без регионов.
- **B (окно = ровно карточка, `DWMWA_WINDOW_CORNER_PREFERENCE = DWMWCP_ROUND`, оконный `DesktopAcrylicBackdrop`, DWM-граница выключена, своя обводка 1 физ. px): углы гладкие** — по зуму дуга радиуса 8 со сглаженной серой обводкой, снаружи дуги значения обоев (0x20–0x26), без чёрных пикселей и ореола. Регион не нужен (`--bregion` включает старый регион для сравнения).
- Новая рекомендация: **вариант B** (карточка двигается как окно по пружине; анимации внутри — Composition). Веер стопки влево — отдельное прозрачное/акриловое окно того же типа (создаётся при раскрытии веера, двигаем пружиной так же) либо расширение окна карточки на время веера. Плавность B на 60 Гц измерена (late=0); на 120/144 Гц — проверка пользователем.
- A оставлен в демо (`--mode A`) только как исследовательский вариант; его уголки/запас не годятся без реальной прозрачности.

### Плитки (S10Spring)
Верхняя плитка Quick Share: сплошная обводка 1 физ. px (тон обводки карточки), внутри заглушка-квадрат 72 epx со скруглением 4 под логотип. Нижняя плитка (стопка): `Rectangle` RadiusX/Y=4, `StrokeThickness = 1/RasterizationScale`, `StrokeDashArray = "4 3"` (единицы — толщина штриха, т.е. физ. пиксели: штрих 4 px / пробел 3 px при любом DPI), тот же полупрозрачный серый. По зуму ×8 пунктир идёт по скруглению без рваных стыков (проверено при 100 %).

## S8 — результаты прогона S8Drive (пользователь запускал сам)

Проверено автотестом (SendInput, реальный OLE drag между окнами тестера и карточкой, NativeAOT-сборка S8Edge):
- **T1/T1b:** Hidden→Peek→Open→Hidden с задержкой скрытия 300 мс; вне полосы по Y (карточка ± 1 см) касание края ничего не делает (PASS).
- **Хук во время OLE-drag:** `WH_MOUSE_LL` получает движения во время drag (`duringLButton` растёт, переходы Peek/Open идут с `lbutton=True`), панель выезжает под drag (PASS).
- **Drop:** `CF_HDROP` (2 файла) — PASS; виртуальный файл `FileGroupDescriptorW`+`FileContents[0]` читается из нативного `IDataObject` (31/31 байт, имя, flags 0x40) — PASS. У WinUI 3 нет `OleDropTargetInterface` на своих HWND → собственный `IDropTarget` через `RegisterDragDrop` на дочерних окнах.
- **Drag-out:** `DragStarting`+`SetStorageItems`, `DropCompleted.DropResult`: принимающая цель → `Copy` и файлы доставлены (элемент удаляется со стопки только при результате ≠ None), отвергающая → `None` (PASS); в S8Edge добавлен лог `shelf count=N` после drag-out как прямое доказательство, что стопка сохранилась.
- **Находка (fullscreen):** `SHQueryUserNotificationState` вернул `QUNS_BUSY (2)` на обычном рабочем столе без fullscreen-приложения — `BUSY` ненадёжен. Теперь подавляем показ при `RUNNING_D3D_FULL_SCREEN`/`PRESENTATION_MODE` или при `BUSY` только если окно переднего плана (кроме Progman/WorkerW/Shell_TrayWnd) покрывает весь основной монитор; в лог каждого перехода пишутся `quns`, признак покрытия и класс окна (без заголовков).
- **Не проверено:** drag из Chrome/Telegram (форматы реальных приложений), большие виртуальные файлы (чтение синхронно внутри `Drop`), поведение при втором мониторе справа от основного, надёжный признак чужого OLE-drag в fullscreen (используется ЛКМ зажата).
